# Slice 3.5 RPC 模式设计

> 日期: 2026-06-23
> 状态: Draft（待用户 review）
> 关联: ARCHITECTURE.md §5 RPC 模式 / §4.8 Verification / §8 Slice 3 / ADR-0001b / Slice 3 verification spec
> 范围: Slice 3.5——cli 第三模式 RPC（JSONL over stdio，JSON-RPC 2.0），接通 Slice 3 verifier 真对话验证。

## 1. 背景与目标

Slice 3 完成了 in-process SantaVerifier（双独立 reviewer + verdict gate + fix loop），但 cli 未接 `verify`——无人能触发对抗验证。本 slice 加 cli 第三模式 RPC，两个目标：

1. **程序化驱动 + 接通 verifier**：让外部程序（IDE/脚本/自动化）经 JSONL 管道驱动 agentforge 对话（`prompt`）与对抗验证（`verify`），收事件流。RPC 暴露 `verify` method，接通 Slice 3 verifier 真对话验证。
2. **建立可扩展协议骨架**：JSON-RPC 2.0 信封，为后续 slice（流式 token / session 管理 / spawn 强隔离）留扩展点（加 method 即可）。

参考：pi `modes/rpc/`（源码在未安装的 pi-coding-agent 包，不可读，按通用 JSONL-over-stdio 设计）；MCP 同 JSON-RPC 2.0 风格。

## 2. 决策汇总（brainstorm 已定）

| 决策点 | 选择 | 依据 |
|---|---|---|
| 范围 | 最小协议（A）：prompt/verify + 事件流，不含 spawn/流式 token/session 管理 method | 先链路后能力 + YAGNI；ADR-0001b spawn 是"可选" |
| 协议风格 | JSON-RPC 2.0 | 标准、可扩展、notification 天然适配事件流、客户端库多 |
| 入口 | `--rpc` flag，index.ts 第三分支 | 与 print/repl 并列，复用路由 |
| 生命周期 | 逐行读 stdin，EOF 退出，无 shutdown method | A 最小 |
| session | JSONL 落盘（复用 repl），协议不暴露管理 method | 可追溯/可 --resume；落盘开销极小 |
| verifier | RPC 默认注入 createSantaVerifier | 接通 verify 是 RPC 核心价值 |
| safety ask | 降级 deny（同 print） | RPC 无交互通道 |
| prompt result | 完整 messages | 客户端无需累积事件即有完整状态 |
| verify 事件 | 不推中间事件 | A 最小，reviewer 独立 Agent 不挂主 EventBus |

## 3. 架构概览

新增 `packages/cli/src/rpc.ts`（`runRpcMode` + JSON-RPC 解析 + 派发 + 事件序列化），遵循 `print-mode.ts`/`repl.ts` 既定模式：核心逻辑抽可测函数 `runRpcMode(argv, deps?)`，bin 入口（`index.ts`）加 `--rpc` 分支调用。

RPC 是第三模式，独立 `runRpcMode`。三者共享 harness 构造材料（6 工具 / systemPrompt / safety / provider / model / getApiKey），IO 与 session 策略不同：

- print: memory session, 一次性, stdout 最终文本
- repl: JSONL session, readline 逐行, stdout 最终文本
- rpc: JSONL session, stdin JSONL 请求, stdout JSONL 响应 + 事件

## 4. 组件与接口

### 4.1 入口路由（index.ts）

`index.ts` 路由优先级：`-p/--print` → print；`--rpc` → rpc；否则 repl。

bin 入口为 RPC 适配 stdin（readline 'line'/'close' 事件 → 行队列，复用 repl 的异步队列桥接模式）与 stdout。

### 4.2 runRpcMode

```ts
interface RpcModeDeps {
  streamFn?: any;          // mock LLM（测试注入）
  getApiKey?: (provider: string) => string | undefined | Promise<string | undefined>;
  input?: { read(): Promise<string | null> };   // mock stdin（JSONL 行队列）
  output?: { write(s: string): void };           // mock stdout（收集 JSONL）
  sessionDir?: string;
  skillDirs?: string[];
  /** 可选注入整个 verifier（测试用 mock；默认 createSantaVerifier）。 */
  verifier?: SantaVerifier;
  /** 可选单请求超时（ms）。prompt/verify 超时 → emit -32603（message 含 "timeout"），中止当前请求，继续读下一行（不杀进程、不丢 session）。未注入时 hang 会阻塞读循环——生产用法建议注入。 */
  promptTimeoutMs?: number;
  onHarnessCreated?: (h: AgentForgeHarness) => void;
}

async function runRpcMode(argv: string[], deps?: RpcModeDeps): Promise<void>
```

- 构造 harness（4.3）→ 推 `ready` notification → 逐行读 input → 解析 JSON-RPC → 派发 method handler → 写响应/事件 → EOF 退出。
- bin 入口：input 适配 process.stdin（readline），output 适配 process.stdout。

### 4.3 harness 构造

复用 repl 的共享构造材料（6 工具 + systemPrompt + safety + cwd + JSONL session + `--resume` initialMessages）。RPC 特有（repl 不含）：verifier 注入。

```ts
const verifier = deps.verifier ?? createSantaVerifier({
  provider: args.provider,
  model: args.model,
  getApiKey,
  streamFn: deps.streamFn,   // 测试 mock；真对话不传走默认
});
const harness = new AgentForgeHarness({
  session, events, tools, provider, model, systemPrompt,
  getApiKey, streamFn: deps.streamFn,
  initialMessages,           // --resume 重建
  safety: createSafetyGuard(),
  // 不传 safetyAskHandler → ask 降级 deny（同 print）
  cwd: process.cwd(),
  verifier,
});
```

- verifier 默认注入；reviewerRun 默认 `createDefaultReviewerRun`（真实 Agent，跑真实 reviewer LLM，需 `DEEPSEEK_API_KEY`）。
- 订阅 `harness.events` → 序列化为 notification 推 stdout（5.2/5.4）。

## 5. 协议 schema（JSON-RPC 2.0）

### 5.1 请求

```json
{"jsonrpc":"2.0","id":<number|string>,"method":"prompt"|"verify","params":{...}}
```

- `id`：客户端生成，number 或 string，关联响应。请求必须有 id（不支持客户端→服务端 notification）。
- `method`：`"prompt"` | `"verify"`。

### 5.2 prompt method

- params: `{input: string}`（用户输入）
- 执行：`harness.prompt(input)`
- 事件流（notification，执行期间推，无 id）：

  ```json
  {"jsonrpc":"2.0","method":"event","params":{"type":"<EventType>",...}}
  ```

  **关联契约**：event notification 无 request id，归属其后的 `result` 所对应请求（sequential 单请求处理，见 §9）。客户端**不得 pipeline**（写多请求再读响应），否则 notification 归属无法解析。未来若加并发，须先给 event params 加 `requestId` 再放宽此约束。

  推 harness EventBus 事件白名单（pi `AgentEvent` 可序列化子集 + harness 自定义）：
  - pi Agent 生命周期/消息事件（`agent_start` / `agent_end` / assistant message 等）
  - harness 自定义：`tool_execution_end` / `compaction` / `context_budget`
  - **不推逐 token 流**（A 约束）
  - 具体白名单在 plan 实现时对照 pi `AgentEvent` 类型枚举（Grep node_modules 失败 `uv_spawn`，plan 用 `require.resolve` 定位 `.pnpm` 下 d.ts；含非序列化字段时白名单映射）

- result:

  ```json
  {"jsonrpc":"2.0","id":<id>,"result":{"messages":[<AgentMessage>]}}
  ```

  完整当前 `AgentMessage[]`（客户端无需累积事件即有完整状态；事件流仅作实时反馈）。

### 5.3 verify method

- params: `{output: string, rubric: Rubric}`
  - `Rubric = {criteria: string[], context?: string}`（对齐 `verification.ts`）
- 执行：`harness.verify(output, rubric)`（委托 `verifier.review`，spawn 2 独立 reviewer + gate）
- 事件流：**不推中间事件**（A 最小；reviewer 独立 Agent 不挂主 EventBus）
- result:

  ```json
  {"jsonrpc":"2.0","id":<id>,"result":<ReviewResult>}
  ```

  `ReviewResult = {verdict: "nice"|"naughty", issues: Issue[], reviews: ReviewerVerdict[]}`
  - `Issue = {severity: "high"|"medium"|"low", description: string, suggestion?: string}`
  - `ReviewerVerdict = {verdict: "nice"|"naughty", issues: Issue[]}`

### 5.4 ready notification（启动）

harness 构造后、读 stdin 前，推一条 notification 告知客户端就绪 + sessionId：

```json
{"jsonrpc":"2.0","method":"ready","params":{"sessionId":"<uuid>"}}
```

**strict gate**：服务端在推 `ready` 前不读 stdin。客户端可等 `ready` 再发首个请求；即使 spawn 后立即写请求，请求缓冲在 stdin，服务端发 `ready` 后按 sequential 处理。`ready` 是严格就绪标志，非 advisory。

### 5.5 错误（JSON-RPC 标准 codes）

| code | 含义 | 触发 |
|---|---|---|
| -32700 | parse error | 行非合法 JSON |
| -32600 | invalid request | 非 JSON-RPC 结构 / 缺 method |
| -32601 | method not found | method 非 prompt/verify |
| -32602 | invalid params | params 缺失/类型错（如 prompt 无 input） |
| -32603 | internal error | harness 抛错（API key 缺失 / prompt 执行异常 / verify reviewer 报错 / LLM 错误）。注：RPC 默认注入 verifier，"verify 未注入"属防御性兜底，正常不触发 |

错误响应：

```json
{"jsonrpc":"2.0","id":<id|null>,"error":{"code":<-32603>,"message":"..."}}
```

parse error 时 id 为 null（无法解析出 id）。

## 6. 数据流

### 6.1 prompt 请求

1. 客户端写 stdin：`{jsonrpc,id,method:"prompt",params:{input}}`
2. 服务端解析 → `harness.prompt(input)`
3. 执行期间 harness EventBus 事件 → 序列化 notification 推 stdout（`tool_execution_end` / assistant message / ...）
4. prompt 完成 → 推 result `{id, result:{messages}}`
5. 继续读下一行

### 6.2 verify 请求

1. 客户端写 stdin：`{jsonrpc,id,method:"verify",params:{output,rubric}}`
2. 服务端解析 → `harness.verify(output, rubric)` → `verifier.review`（spawn 2 reviewer + gate）
3. 无中间事件
4. 推 result `{id, result: ReviewResult}`

## 7. 错误处理

- JSON 解析失败 → `-32700`（id=null）
- 非 JSON-RPC / 缺 method → `-32600`
- 未知 method → `-32601`
- params 缺失/类型错 → `-32602`
- harness 抛错（API key 缺失 / prompt LLM 错 / verify reviewer 错）→ `-32603`，message 含错误信息。注：RPC 默认注入 verifier，"verify 未注入"属防御性兜底（正常不触发，仅当 deps.verifier 显式传 undefined）
- 每个 error 写一行 stdout，**继续读下一行**（不退出进程，除非 EOF）——单请求错误不杀 RPC 进程
- safety deny：prompt 内工具被 safety 拦 → `tool_execution_end` 事件含 `isError`，prompt 正常完成（不报 RPC 错）
- **prompt/verify hang 防护**：`deps.promptTimeoutMs` 注入时，单请求超时 → emit `-32603`（message 含 "timeout"），中止当前请求（pi Agent `signal` / `Promise.race`，具体机制 plan 定），**继续读下一行**（不杀进程、不丢 session）。未注入 timeout 时 hang 会阻塞整个读循环——生产用法建议注入。harness 当前 `prompt()` 不接受 signal，超时中止的实现路径（改 harness 加 signal vs Promise.race 包裹）plan 阶段定。

## 8. 测试策略（TDD，per-test RED-GREEN-REFACTOR）

项目硬约束：无失败测试不写生产代码，严格 per-test RED。`runRpcMode` 可测函数 + deps 注入（mock streamFn / mock stdin / mock stdout）。

覆盖：

1. `ready` notification 含 sessionId
2. prompt 请求 → 事件 notification（`tool_execution_end` / assistant message）+ result messages，mock streamFn 控制助手回复 + 工具调用
3. verify 请求 → result `ReviewResult`，deps.verifier 注入 mock verifier 控制结论（不调真实 LLM）
4. 错误码：`-32700` parse / `-32601` method not found / `-32602` invalid params / `-32603` internal（prompt 抛错 / verify reviewer 抛错）
5. EOF 退出（`input.read` 返回 null → 循环结束）
6. JSONL 落盘（session 文件含 message entries）
7. `--resume` 重建 messages
8. safety deny → `tool_execution_end` isError 事件，prompt 正常 result
9. 多请求顺序处理（prompt 后 verify）

mock：streamFn 控制助手/工具；deps.verifier 注入 mock verifier 控制 verify 结论；input 注入 JSONL 行队列；output 收集输出 JSONL 断言。

## 9. 范围边界（本 slice 不做）

- 独立进程 spawn 强隔离（ADR-0001b Revisit）
- 流式 token 事件（逐 token 推）
- session 管理 method（new/resume/list）——session 由 `--session` flag 启动时定，协议不暴露运行时管理
- 交互式 safety ask（ask 降级 deny）
- 多并发请求（单请求顺序处理）
- cli `verify` 子命令（非 RPC）——留后续

## 10. 默认值

- method 集合：prompt / verify
- session：JSONL 落盘，sessionId 自动 UUID 或 `--session` 指定
- verifier：默认注入
- safety ask：降级 deny
- 错误码：JSON-RPC 2.0 标准

## 11. 风险与待定

- **事件白名单**：pi `AgentEvent` 完整成员待 plan 阶段枚举（`require.resolve` 定位 `.pnpm` 下 d.ts）；含非序列化字段时白名单映射。
- **AgentMessage 序列化（plan 首个 task 必须验证）**：`harness.ts:237-242` 持久化时用 `entryId: "" as any` 占位，是 `AgentMessage`/`MessageEntry` 形态未净的信号。RPC `result.messages` 同样依赖 JSON 序列化。plan 首个 task 写序列化往返测试（`AgentMessage` → `JSON.stringify` → `parse` → 深相等），若含 undefined/函数/循环字段则 result schema 需白名单映射，再定 result 形态。
- **verifier 真跑需 DEEPSEEK_API_KEY**：测试 mock reviewerRun 绕开；真对话需 env key（旧 key 需轮换）。
- **parseArgs 加 --rpc**：改 `print-mode.ts` parseArgs 或 `rpc.ts` 自带解析——plan 阶段定（倾向复用 parseArgs 加 rpc flag）。
